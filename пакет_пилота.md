## 1. Что считать пилотом

Пилот — это не "первые продажи ради теста".

Пилот — это короткий управляемый запуск, который должен дать:
- ранние артефакт результатаs;
- реальные данные по прохождению;
- реальные сигналы полезности;
- материал для B2C и B2B продажи следующей волны.

## 2. Что запускать первым

### Приоритет по умолчанию

Сначала запускать:
- `B2C Beta Cohort`

Потом:
- `B2B Mini-Pilot`

Почему:
- B2C beta быстрее дает первая практическая победаs, цитаты и понятные артефакт результатаs;
- B2B pilot лучше запускать уже не с пустыми руками, а с первыми подтвержденными кейсами.

## 3. Формат 1. B2C Beta Cohort

### Рекомендуемый размер

- `12-20 участников`

### Рекомендуемая длительность

- `14 дней прохождения`
- `3-5 дней на сбор итогов`

### Что входит

1. Сессия 0.
2. базовый модуль.
3. Домашние 1, 2, 3, 5.
4. Mini-project.
5. Входная и выходная диагностика.
6. Сбор первая практическая победа, шаблонов и план внедренияs.

### Что должно выйти на выходе

1. Не менее 8-10 первая практическая победаs.
2. Не менее 8 repeatable scenarios.
3. Не менее 6 пригодных шаблонов.
4. Не менее 5 mini-projects, которые не стыдно показывать.
5. Не менее 3 сильных цитат языком работы.

## 4. Формат 2. B2B Mini-Pilot

### Рекомендуемый размер

- `10-20 участников`
- `1 owner со стороны компании`
- `1 общий сценарий`

### Рекомендуемая длительность

- `14 дней прохождения`
- `1 midpoint-check`
- `1 финальный review`

### Что входит

1. базовый модуль.
2. Входная и выходная диагностика.
3. Один общий сценарий команды.
4. Один общий шаблон.
5. Один общий чек-лист.
6. Короткий pilot report для owner / ЛПР.

### Что должно выйти на выходе

1. Один общий сценарий, который команда реально опробовала.
2. Один общий шаблон.
3. Один общий чек-лист.
4. Один короткий metric signal.
5. Один manager summary.
6. Один group report.
7. Одно решение: `масштабировать / доработать / сузить`.

## 5. Launch gate

Во внешний пилот можно идти только если одновременно выполнены 5 условий:
1. Сессия 0 и ранний блок прошли внутренний QA.
2. Участник может пройти путь от входа до первой домашки без ручного сопровождения.
3. Proof artifacts действительно собираются.
4. Есть working бриф участника.
5. Есть working operating board и owner-side logic.

## 6. Календарь пилота по дням

### День 0

- онбординг;
- рассылка brief;
- входная диагностика.

### День 1-2

- сессия 0;
- фиксация первая практическая победа;
- сравнение до / после.

### День 3-5

- уроки 1-5;
- домашняя 1;
- первые шаблоны.

### День 6-9

- уроки 6-15;
- домашние 2 и 3;
- проверка repeatable scenarios.

### День 10-14

- уроки 16-24;
- домашняя 5;
- mini-project;
- 14-day plan.

### День 15-19

- сбор метрик;
- сбор цитат;
- сбор артефакт результатаs;
- pilot report;
- решение по следующему шагу.

## 7. Что нужно собрать во время пилота

### Обязательно

1. Сколько людей начали.
2. Сколько прошли сессию 0.
3. Сколько зафиксировали первая практическая победа.
4. Сколько дошли до урока 5.
5. Сколько сдали домашние.
6. Сколько дошли до mini-project.
7. У скольких появился repeatable scenario.
8. У скольких появился рабочий шаблон.

### Для B2B дополнительно

1. Есть ли общий сценарий.
2. Есть ли общий шаблон.
3. Есть ли общий чек-лист.
4. Есть ли одна понятная рабочая метрика.

## 8. Что считать хорошим пилотом

Хороший пилот — это не “людям понравилось”.

Хороший пилот — это когда:
1. early value появляется быстро;
2. люди действительно что-то внедряют;
3. остаются реальные рабочие артефакты;
4. можно честно принимать бизнес-решение.

## 9. Что считать плохим пилотом

Плохой пилот — это когда:
1. участники смотрят, но не применяют;
2. есть интерес, но нет repeatable use;
3. нет ни одного сильного артефакт результата;
4. на выходе невозможно объяснить, что именно изменилось.

## 10. Какие решения можно принять после пилота

### Вариант 1. Scale

Когда:
- activation и первая практическая победа сильные;
- есть repeatable use;
- есть артефакт результатаs;
- есть уверенность в следующей волне.

### Вариант 2. Improve And Repeat

Когда:
- полезность есть;
- но user path, домашки или visual layer мешают результату.

### Вариант 3. Narrow

Когда:
- общий курс слишком широк;
- а один сценарий использования или одна функция уже показывает полезность.

### Вариант 4. Stop

Когда:
- нет activation;
- нет early value;
- нет repeatable use;
- и нет смысла масштабировать сырой продукт.

## 11. С чем должен выйти владелец проекта

После пилота у владельца должны быть:
1. pilot report;
2. 3-5 цитат;
3. 3-5 артефакт результатаs;
4. shortlist сильных и слабых мест;
5. решение по следующему запуску.
